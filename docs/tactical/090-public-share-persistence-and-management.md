# Replace Aggregate Public-Share Persistence and Add Global Management

> Replace the boot-loaded aggregate public-share JSON object with
> independently stored share state plus a compact link-grant store, then let
> an authenticated owner inspect and revoke every surviving link without
> loading frozen transcripts.

Status: Final implementation handoff. The current-state measurements, storage
shape, authorization semantics, and management UX are established. No storage
migration, management route, or management UI described here is implemented
yet. The new client/server contract still needs the compatibility approval
quoted below before editing. Delete this tactical ledger after implementation
and verification; the lasting product contracts belong in the related topic
docs.

## Why this is open

`PublicShareService` currently persists every public share record in one YA
app-data file, `public-shares.json`. A frozen record embeds a complete
sanitized `AppSession`; a viewer-specific freeze embeds another snapshot in
the same record. `initialize()` reads and parses the complete file, retaining
every body in `state.shares`. Every create, update, freeze, or revoke calls
`save()`, which pretty-stringifies and rewrites the complete state.

The frozen `AppSession` is structured session JSON, not an as-rendered DOM or
a worktree snapshot. It can contain server-produced `_html`, diff, and
highlight augments, but React reconstructs the page through `MessageList` and
client-only glossary context is absent. For a rewritten public file link, the
server currently traverses strings in that stored session to check that the
requested path was mentioned, then reads the file from the current project.
Transitive render assets are discovered by rereading current Markdown/HTML.
Thus a frozen transcript may expose later file contents, and its incidental
render augments are not a complete captured presentation or capability list.

The measured operator store was 501,910,755 bytes and contained 46 still-valid
links: 28 frozen links and 18 live links. It had no revoked tombstones. A
short-lived isolated process measured approximately:

| Phase | V8 heap | Resident set / peak |
|---|---:|---:|
| Before read | 4.6 MiB | negligible baseline |
| UTF-8 file read | 0.98 GiB | about 1.04 GiB RSS |
| `JSON.parse` retained state | 1.55 GiB | about 1.72 GiB RSS; 1.95 GiB peak |
| pretty `JSON.stringify` of unchanged state | 2.48 GiB | about 2.65 GiB RSS; 3.50 GiB peak |

Values use GiB where converted from the byte measurements. The exact raw
measurements are retained with tactical 089. The live server's V8 heap limit
was about 4.19 GiB, so the canonical share object alone consumed a large
fraction of the limit and a whole-state save could collide with transcript
parse transients and other retained caches.

These records are persistent bearer capabilities, not share history. A record
exists because its URL remains valid after reboot. An inactive viewer does not
make a link obsolete. “Stop live updates” converts a live link into a frozen
link and retains a snapshot; only revocation invalidates and releases it.

## Current management and revocation

Management is implemented only at two coarse scopes:

- Turning off **Public Read-Only Share** in Remote Access settings persists
  `publicSharesEnabled: false`, calls `PublicShareService.revokeAllShares()`,
  hides the broadcast controls, and makes public routes return not found. This
  is an intentional destructive kill switch, not merely toolbar visibility.
- The session broadcast popup can inspect aggregate counts for its source
  session and revoke every link for that session through `DELETE
  /api/public-shares/sessions/:projectId/:sessionId`.

There is no global valid-link inventory and no way to revoke one selected
link. Finding a surviving link otherwise requires revisiting its source
session. The popup's viewer-token freeze and disconnect actions do not fill
that gap: the token is generated by a browser tab, is replaceable, and is not
a person or bearer authorization. Only revoking the link prevents a holder
from opening it again.

The existing per-session controls also have a false-empty startup state.
`PublicShareService.initialize()` loads and parses the aggregate in the
background while `state.shares` remains empty. A session-status request during
that interval returns zero rather than “still opening,” so
`SessionShareModal` hides its management block. The modal polls every 10
seconds; after a multi-second aggregate load, management can remain absent for
almost another full poll interval. If file read, validation, or parsing fails,
`initialize()` leaves the empty state in place (read/parse errors log only;
invalid shape has no actionable state), so the popup can hide management
forever while continuing to report a false zero.
This is not merely slow rendering—the server reports the wrong authorization
inventory and has no actionable failed state.

## Vocabulary and ownership

- A **valid share link** is a public URL whose secret still authenticates one
  public read-only share. Valid does not mean that a viewer is connected.
- A **bearer capability** is that secret-bearing URL and the read authority it
  grants. The link, not a viewer token or active connection, is the revocable
  authorization unit.
- A **link grant** is the small authorization record that maps one hashed
  bearer secret to a share-state id and either its live view or one immutable
  frozen revision. Revoked links have no valid grant and no serving tombstone.
- **Share state** is the independently stored public projection for one source
  YA session. At most one live share state exists for that source session;
  multiple URLs are grants over it, not duplicate live records.
- A **frozen revision** is an immutable, pre-sanitized public view selected by
  a grant. The first implementation stores a response-ready compressed copy;
  a later implementation may select an immutable share-owned turn prefix.
  Neither representation is part of the management inventory or loaded at
  server startup.
- A **management inventory** is compact authenticated metadata over valid
  links. It never includes a share secret, secret hash, transcript body, or
  project filesystem path.
- A **viewer token** is ephemeral, browser-generated operational state used for
  live-view counts and viewer-specific freezing. It is not authenticated
  identity and cannot support a security claim such as “revoke this person.”

The persistent owner is YA app data. No share index, snapshot, migration
marker, cache, or garbage-collection state may be written into the selected
project or its Git metadata.

## Design decisions

- **Keep SHA-512 as the direct authorization key** (vs. a new SHA-256 key):
  legacy storage has only the SHA-512 result, so this is the only direct key
  that can preserve every old URL without seeing it again. This does not
  require new secrets to remain 512 bits.
- **Generate 128-bit opaque secrets for new links** (vs. the current 512-bit
  value): 16 CSPRNG bytes encode to 22 base64url characters and retain the
  recommended entropy for a custom unguessable web token. Continue accepting
  the exact 64-byte legacy form so every existing 86-character secret works.
- **Use gzip as the portable snapshot codec** (vs. mandatory zstd): YA's Node
  20.12 runtime floor supplies streaming gzip but not native zstd. The stored
  representation must work at the supported floor.
- **Separate compact grants from large share state** (vs. organizing
  authorization records and bodies together per session): the grant store is
  the only authority for valid URLs and may use any atomic bounded format.
  Each share-state directory owns only one session's public projection and
  immutable revisions.
- **Copy the first frozen representation** (vs. raw source byte ranges): a
  provider transcript or ordinary JSON response may be rewritten and is not a
  safe immutable prefix. Content-addressed compressed copies give the required
  contract now. A later prefix representation must point into immutable,
  share-owned chunks or turns, never a mutable provider file.
- **Freeze project files only with a real copy-on-write clone**: when the
  source and app-data filesystems support an atomic/recoverable CoW project-tree
  clone, a frozen revision owns that clone. When they do not, preserve the
  current live-project-file behavior and label it prominently; do not perform
  an unbounded physical worktree copy. “Unsupported” is a deliberate fallback,
  while an unexpected clone failure aborts creation instead of silently
  changing semantics.
- **Keep Settings disable destructive** (vs. dormant links): this preserves
  current behavior and the security meaning of turning a public facility off.
  Confirmation and global management make the consequence explicit.
- **Offer both discoverable and direct management entry points**: ordinary
  left click keeps the share/create popup, right click opens that session's
  management panel directly, and the popup and Settings retain ordinary links
  for keyboard, touch, and discoverability.
- **Persist the compact public header on the server** (vs. carrying display
  hints in the copied URL): a new link contains only routing parameters, its
  short bearer secret, and a compact protocol marker. The public viewer fetches
  title, initial-prompt preview, project display name, mode, and capture time
  without opening the transcript body.
- **Treat viewer tokens as operational state** (vs. user authorization): the
  browser chooses them and a link holder can replace them, so only bearer-link
  revocation carries an access-control claim.
- **Separate management from creation readiness** (vs. reusing `canCreate`):
  an owner must be able to inspect and revoke stored links after relay or
  Remote Access configuration becomes unavailable.

## Target store

Use a compact authorization store plus one independent state directory per
shared source session. This tree is schematic: the grant store's file/database
format is deliberately an implementation detail so long as it remains atomic,
bounded by valid-link count, and contains no transcript bodies.

```text
<data-dir>/public-shares/
├─ grants.<implementation-owned>
├─ shares/
│  └─ <opaque-share-state-id>/
│     ├─ state.json
│     └─ frozen/
│        └─ <revision-id>/
│           ├─ session.json.gz
│           ├─ presentation.json
│           └─ project/          # only when a CoW clone is supported
└─ migration.json
```

The incoming URL supplies a 128-bit new secret or a 512-bit legacy secret. YA
hashes either with the existing SHA-512 function and performs a direct lookup
in the compact grant store. A grant contains opaque `shareId`,
`shareStateId`, source-session identity for management, a target of `live` or
one frozen revision, and the bounded display metadata needed for inventory and
the public header. It retains timing-safe validation of the supplied secret
against the stored hash. The plaintext secret is returned once and never
persisted.

The grant store is the sole source of truth for valid links. Authenticated
inventory and per-session status query it directly; they do not enumerate
share-state directories. State files and frozen revisions can never recreate
a deleted grant or make a revoked URL valid. Since this store scales with
compact valid-link metadata rather than transcript bytes, opening it is a
bounded control-plane operation; its serialization format need not be grouped
by session.

Derive or allocate the opaque share-state id without exposing a project path
or replacing the YA-visible session id. `state.json` contains the canonical
source identity, compact public header, current live projection metadata, and
frozen-revision references. A second live grant for the same source session
reuses this state rather than creating another live record. Frozen and live
grants can coexist and may select different revisions of the same share state.

For the first implementation, store each distinct frozen revision as
streaming gzip, content-addressed within its share-state directory. Gzip is
available at YA's Node 20.12 runtime floor; native zstd is not. The revision id
names the exact uncompressed, sanitized, response-ready session bytes and
excludes grant-specific timestamps and metadata. Two grants over the same
sanitized revision therefore share one body. Revocation deletes a revision
only after no grant or viewer-specific freeze refers to it. Keeping revisions
local to one share state prevents one session's lifecycle and access pattern
from coupling another's.

At capture time, attempt the project's supported copy-on-write tree-clone
primitive from the selected project into the frozen revision. Capability must
be established by the actual operation on the source and destination
filesystems, not inferred from the OS name. The clone is app-data persistence,
not new authorization: the public viewer can still open only paths authorized
by the captured transcript/presentation manifest, and Git metadata is not a
public asset. When CoW is unsupported, record `linkedFileMode: live` and keep
the existing behavior of resolving an authorized link against the current
project tree. The owner-facing creation UI and the public frozen viewer both
show a persistent warning such as **Transcript frozen; linked project files
remain live and may expose later contents.** The compact public metadata route
must carry this mode so the warning appears before the transcript loads.

`presentation.json` may retain enrichment decisions that were already known
when the revision was captured. In particular, it may replay exact
path-existence autolinks with opaque authorized targets and the glossary
definitions actually used by shared content. It must not rescan or validate
the project merely to enrich a share, expose a public path-existence oracle,
subscribe a public viewer to the authenticated glossary service, or ship an
entire unused glossary. Unknown enrichment is omitted without affecting share
correctness. This is low-priority reuse of known results, not a prerequisite
for the storage migration. Do not add a presentation abstraction or another
layer to the standard session/file render pipeline for this purpose. Capture
only at an existing augment/result boundary with local plumbing; if that is not
enough, omit the enrichment from shares.

A future turn-prefix representation is valid only if the share store owns an
immutable append-only sequence whose cursor cannot change meaning. A raw byte
range into a provider transcript, a mutable source file, or a JSON response is
invalid: provider formats can be rewritten and a normal JSON document changes
suffix bytes as it grows. The grant's logical `live`/revision target must not
change if the physical revision representation changes later.

Prefer a response-ready serialized body that can be decompressed and streamed
without constructing a complete `AppSession` object. Precompute any bounded
metadata the public file-capability route needs when the snapshot is created;
serving a mentioned file must not reparse the transcript body merely to decide
authorization. If the existing response envelope needs dynamic metadata,
stream the fixed prefix, frozen body, and suffix rather than parsing and
re-stringifying the body.

The live share state resolves the current source session on demand or stores a
bounded public projection cache; it never embeds that session in the grant
store. A viewer-specific freeze becomes another immutable revision selected
by that grant. Viewer heartbeat/access state remains ephemeral unless a
specific persisted behavior requires otherwise.

## Compact public links and immediate header

The current generated URL contains an 86-character, 512-bit secret plus
fragment hints for mode, project name, capture time, title, and as many as 700
characters of the initial prompt. Those hints exist only to render useful
content while the combined transcript response is loading. They make the URL
long and couple basic page identity to body latency.

For new links, generate 16 random bytes and encode them as an unpadded
22-character base64url bearer secret. Persist a bounded public header with the
grant/share state: title, public-safe initial-prompt preview, project display
name, mode, created/captured time, provider when present, and the frozen
revision's linked-file mode. Derive the preview from the same share-visible,
censored projection as the public body; never copy an unsanitized source-only
field into this fast path.

Add `GET /public-api/shares/:secret/metadata`, authorized by the same bearer
secret, which reads one compact grant and one small state record and never
opens a transcript revision or project file. The hosted viewer requests this
metadata immediately and renders the subject/preview/warning while fetching
the large body separately. A new URL carries no display text; it retains the
required `h` relay username, optional non-default `r` relay URL, and a compact
fragment protocol marker such as `#v=2`. The marker tells a new viewer that the
metadata route exists. An old viewer ignores it and still loads the combined
body; a new viewer uses legacy display fragments on old links and sends no
unsupported metadata request.

Existing 512-bit links and their verbose fragments remain valid. The server
accepts exactly the new 16-byte and legacy 64-byte decoded secret forms, rather
than weakening validation to arbitrary lengths. Both hash to the same SHA-512
grant-lookup namespace.

## Mutation and crash contract

Normal content mutations serialize per share-state directory; grant changes
use the compact store's atomic transaction or replacement primitive.
Migration, global revocation, and global enable/disable also take a store-wide
authorization barrier so they cannot race a create in another session.
Enforce owner-only permissions on the complete store, including `0700`
directories and `0600` grants, state, revisions, CoW clones, migration state,
and legacy backup on POSIX plus the existing owner-ACL equivalent on Windows.
Use an atomic temp-write-plus-rename facility for file-backed records; do not
expose partially written metadata or compressed bodies. Fsync the file and
parent directory at authorization commit points where the supported platform
permits it, and test the weaker platform path explicitly rather than calling a
rename alone “durable.”

Creating a link is fail-closed:

1. create/reuse the share state and write its frozen revision, optional CoW
   project clone, and presentation state;
2. atomically write the updated small share-state metadata;
3. atomically insert the link grant last; and
4. return the URL only after that grant is durable.

A crash before step 3 may leave unreferenced garbage but cannot expose an
incomplete link. A later bounded collector removes revisions and empty share
states that no grant owns.

Revocation invalidates first:

1. atomically delete the link grant from the serving grant store;
2. commit that invalidation before content cleanup;
3. delete newly unreferenced revisions and their CoW clones; and
4. remove the share-state directory when no valid grant refers to it.

Once step 1 succeeds, the URL must fail even if cleanup is interrupted. Do not
restore authorization from leftover share state during recovery. Per-session
revocation selects every matching grant from the compact store; global
revocation invalidates all grants, then collects unreferenced share states.
“Stop live updates” is a revision/grant-pointer transaction, not revocation:
write the immutable revision first, then atomically retarget the still-valid
grant from `live` to that revision.

The Settings toggle remains the destructive global kill switch. Disabling
first persists `publicSharesEnabled: false`, which immediately gates creation
and public reads, then resumes the same store-wide revoke transaction until no
live authorization record remains. A cleanup failure leaves the feature off
and must be visible; it must not roll the setting back to enabled. Re-enabling
first finishes any interrupted disable cleanup under the global barrier, so an
old record can never be resurrected by flipping the toggle back on. When valid
links exist, the client confirms the count and consequence before sending the
disable request.

The store is gated by valid links, not by connected viewers or cache recency.
Do not automatically expire a valid link as part of this migration. Expiry is
a separate product policy requiring visible owner semantics. The manager is
the immediate way to find and revoke forgotten links.

## Legacy migration without a boot heap spike

Preserve every existing URL, including its 512-bit secret and display fragment;
only newly created links use the compact shape. Migrate the legacy
`public-shares.json` once with a streaming reader specialized
for the legacy top-level `{ "shares": [...] }` shape and its nested
`frozenSession` / viewer-snapshot bodies. It may `JSON.parse` compact record
metadata after replacing those bodies with references; it must stream each
already-sanitized body subtree through JSON whitespace canonicalization,
content hashing, gzip, and bounded file-capability extraction without parsing
the complete `AppSession`. This keeps the actual bound to one compact share
record plus one body, even when one legacy record contains several
viewer-specific snapshots. A whole-file or whole-body `readFile`,
`JSON.parse`, or `JSON.stringify` is not an acceptable migration
implementation. The parser must be chunk-boundary, escape, Unicode, nesting,
malformed-tail, and trailing-field tested rather than treated as a general
JSON parser.

Migration runs in the background after the ordinary server binds. Until the
durable completion marker exists:

- existing public-link requests return a bounded retryable unavailable
  response rather than treating links as revoked;
- share creation, freezing, per-link/session mutation, and management return a
  clear
  migration-in-progress response so two storage formats cannot diverge; and
- ordinary authenticated session use remains available.

The service exposes explicit `opening`, `migrating`, `ready`, `failed`, and
`disabled` readiness states. The bounded opening step reads only control state
and directory metadata; it never scans authorization records or snapshot
bodies. Before opening completes, share reads and mutations return the same
retryable unavailable class as migration rather than a false not-found or an
empty-store success. A disabled service returns not found on public reads by
policy, while authenticated status explains that the feature is disabled.

Authenticated global and per-session status distinguish `opening` /
`migrating` / `failed` from a ready empty result. The client renders the
management region immediately with a disabled **Loading existing shares…** or
actionable failure state; it never interprets not-ready as zero. Once ready,
per-session status filters compact grants and resolves without the 10-second
polling delay or any share-state/body read. Typed retryable status on the
existing status route is an additive recovery path; older clients may keep
their current retry behavior, while current clients show the real state.

The global Settings kill switch is the exception: it must remain available
during migration. Persisting `publicSharesEnabled: false` immediately keeps all
public reads unavailable, cancels further authorization publication, and moves
the legacy aggregate to its non-serving backup disposition. It then records a
durable disabled/revoked completion state so re-enable starts empty rather than
resuming publication from the backup. A migration must never trap the owner in
an enabled public facility with no revocation path.

If `publicSharesEnabled` is false, legacy records are already revoked by the
kill-switch contract. Preserve the aggregate file under its non-serving backup
name, but do not emit new authorization records from it. A later re-enable
starts with an empty store and cannot resurrect those links.

Write each new revision/share state and grant using the normal create ordering.
Group legacy live records for the same canonical source session into one live
share state while preserving separate grants and per-link display metadata.
Legacy frozen records cannot recover an as-of worktree snapshot; mark their
linked-file mode as live and show the same warning as a new frozen share on a
filesystem without CoW support. After every legacy record is durable,
atomically rename the legacy file to its non-serving backup name, then
atomically write the durable completion marker, and only then allow mutations.
An interruption between the
rename and marker must resume from the backup path. Removing that backup is an
explicit later cleanup, not part of the first successful boot. Invalid legacy
input must preserve the source file and report a bounded actionable error;
never replace it with an empty store.

The migrator must resume idempotently after interruption. Existing matching
records and bodies are verified/reused; a conflict fails closed rather than
silently choosing one copy. Record counts, source byte offset, migrated body
bytes, elapsed time, and peak process memory belong in bounded performance
events, without secrets or transcript text.

Disk exhaustion or another write failure leaves the legacy source/backup and
all previously durable new records intact, removes only uncommitted temp files,
and withholds the completion marker. It must not turn the aggregate into an
empty store or prevent ordinary authenticated session use; status reports the
actionable migration failure and a later restart can resume after space is
freed.

## Global management contract

Add an authenticated, paginated inventory over the compact grant store. The
server must not open a share-state directory, frozen body, or CoW project clone
to answer it. Each row includes:

- opaque `shareId`, mode, title, project display name, YA session id, provider;
- created, updated, and captured timestamps;
- current live-viewer count and whether viewer-specific freezes exist; and
- the snapshot's stored byte size, never its content.

Existing records keep only a hash of the bearer secret, so the manager cannot
reconstruct or copy an old URL. It may identify and revoke the link. Creating
a replacement is an explicit session action that produces a new secret.
Rows manage bearer capabilities, not people: viewer tokens may supply
ephemeral activity detail, but no row or action may label a token as an
authenticated user or claim that disconnecting it prevents a link holder from
returning.

Management readiness is independent of share-creation readiness. Inventory and
revocation use the local authenticated server and remain available while the
feature is enabled even if relay credentials are missing, Remote Access is
disabled, or the relay is disconnected. Those conditions may disable creation
and public reachability; they must not hide the controls needed to retire
stored capabilities.

Proposed routes:

- `GET /api/public-shares?cursor=&limit=&projectId=&sessionId=&mode=` — compact
  valid-link inventory;
- `DELETE /api/public-shares/:shareId` — revoke one link; and
- `POST /api/public-shares/revoke-all` with body
  `{ "confirmation": "revoke-all-public-shares" }` — revoke every link after
  explicit confirmation.

Put these three routes in a capability-owned management route module separate
from the existing create/status/session/viewer module. The capability audit's
`routeModules` contract requires every route in a named module to belong to
that capability; the pre-existing public-share routes must not be accidentally
claimed as new management support.

Keep the existing per-session status, freeze, viewer, and revoke routes and
their semantics. The new one-link delete should use an opaque non-secret
`shareId`, not accept a secret hash from the client.

The session-header broadcast indicator remains the in-context entry point:

- ordinary left click opens the existing session share popup;
- right click bypasses that popup and opens the shared manager already filtered
  to the current session;
- that popup adds **Manage this session's shares**, which opens the shared
  manager filtered to the current session without creating a link;
- Remote Access settings adds a canonical, searchable **Manage all public
  shares** `SettingsItem` beside the destructive feature toggle, using the same
  manager; and
- when management capability is absent, both entries are hidden, right click
  remains browser-owned, Settings retains its existing toggle, and the
  existing per-session share UI is unchanged.

Use one modal/controller with `session` and `manage` views rather than a second
implementation of share status. The manager supports pagination and filters,
confirms one-link and global revocation, updates rows after mutation, and does
not poll when closed. It should reuse the existing session popup's per-session
status after returning from management. The current viewer-token action should
be labeled as an operational tab disconnect, with an explicit warning that a
link holder can reopen the URL; only link revocation is presented as access
revocation. In the session surface, creation buttons follow `canCreate`, while
the broadcast indicator and management controls remain visible when that
session has valid links. Session-status polling follows feature enablement,
not creation readiness.

The Settings row declares searchable label, description, and keywords for
`public share`, `broadcast`, `link`, `manage`, and `revoke`, so the same search
that finds the feature toggle also exposes the real management action. It is
operable directly from Settings search results under the existing shared-row
contract.

## Compatibility review checkpoint

This is optional functionality. On 2026-08-05, the required release corpus is
the latest two stable server releases: `0.7.0` (2026-07-25) and `0.6.2`
(2026-07-11). `0.7.0` is also the only stable release in the preceding 14-day
window. Both have the existing public-share create/status/session-revoke
family. Neither has global inventory, one-link revocation by opaque id, or a
capability advertising those contracts.

Add a new permanent `public-share-management` capability. It owns the three
proposed routes and their compact response fields. Do not broaden another
advertised capability. Without it, the client hides both management entries,
leaves right click browser-owned, and makes no inventory or new revocation
request. Existing per-session sharing, the destructive Settings toggle, and
older capable behavior remain unchanged. The content/grant storage split is
server-internal. Compact links use their own per-link fragment protocol marker:
an older viewer can still fetch their combined response, while a new viewer
never calls the metadata route for an unmarked legacy link.

Approval to obtain before client/server contract edits:

> Compatibility review for public-share management: releases `0.7.0` and
> `0.6.2` lack global inventory, opaque one-link revocation, and global
> revocation routes. Add permanent capability `public-share-management` for
> `GET /api/public-shares`, `DELETE /api/public-shares/:shareId`, and `POST
> /api/public-shares/revoke-all`; without it the client hides the broadcast and
> Settings management entries, preserves the browser context menu, and makes
> no unsupported request. New compact links mark support for the additive
> public metadata route in the link itself; old viewers keep using the combined
> response and new viewers do not probe old servers. Existing links,
> per-session routes, the destructive Settings toggle, capability meanings,
> and older behavior remain unchanged. Approve?

## Recommended implementation sequence

### 1 — separate compact grants from independent share state

Implement the compact grant store, independent share-state directories, one
live state per source session, response-ready frozen transcript copies, and
atomic mutation ordering. Add conditional whole-project CoW capture with the
explicit live-file warning fallback. Unit-test
interrupted create, freeze, single revoke, session revoke, disable, re-enable,
global revoke, and garbage collection at every transaction boundary.

### 2 — stream the aggregate-file migration

Build an idempotent record-at-a-time migrator with a durable completion marker
and retryable route readiness. Test a fixture with several large records,
duplicate snapshots, viewer-specific freezes, the legacy empty-message frozen
body repair case, malformed trailing input, and restart after every durable
step. A legacy body that currently requires source-session repair must either
be repaired before its new authorization record becomes live or retain an
explicit unavailable/repair state; migration must not canonize the broken body
as a successful frozen share.

### 3 — serve one share state without loading the others

Route secret lookup through the grant store and stream one selected frozen
revision. Keep live-share resolution and existing link rewriting. If a CoW
project snapshot exists, serve authorized linked files from it; otherwise use
the live project with the recorded warning. Verify legacy URLs before and
after migration and prove that serving one revision does not read another.

### 4 — add compact authenticated management routes

After compatibility approval, register `public-share-management`, add bounded

## Acceptance

- A server with an aggregate fixture equivalent to the measured 502 MB store
  binds and serves ordinary health/session requests without reading or parsing
  frozen bodies. Post-start heap is independent of total frozen-body bytes.
- Migration materializes no more than one legacy record/body at a time; record
  count and URL validity match before/after, and an interrupted migration
  resumes without duplicate valid links or lost revocations.
- A frozen transcript request loads/streams only its selected revision; a
  linked-file request reads only the authorized path from that revision's CoW
  snapshot or warned live fallback. Global inventory loads zero share states,
  transcript bodies, and project snapshots. Every revoke operation loads zero
  transcript bodies and invalidates the compact grant first.
- Opening the broadcast popup during store opening or migration immediately
  shows a loading management region, never a false zero-share result. Once the
  store is ready, the session's controls resolve from its compact grants
  without waiting for a global scan or the next 10-second poll.
- Creating or freezing one link never serializes or rewrites another share
  state's metadata or revision. Revoking a link atomically updates only the
  small grant store before collecting its now-unreferenced state.
- Revocation invalidates the URL before cleanup; no tested crash point makes a
  revoked URL valid again. The last revocation removes the empty share state
  after bounded garbage collection.
- Two frozen links to the same revision share one state-local body;
  it survives until the final reference is revoked.
- Left click still opens session sharing and creates nothing by itself. Its
  management entry and right click both open the inventory filtered to that
  session; Remote Access settings opens the all-share inventory. With an older
  server the new entries and interception are absent, so no unsupported
  request is sent and the browser context menu remains unchanged.
- A new link uses a 22-character opaque secret and contains no project, title,
  or initial-prompt display text. Its compact metadata renders before the
  transcript body is read. Existing 86-character-secret links remain valid and
  new/old viewer combinations follow the explicit link-version fallback.
- On a supported source/destination filesystem, a frozen linked file resolves
  from the revision's CoW project snapshot and does not change after the source
  worktree changes. On an unsupported filesystem, the frozen owner/viewer UI
  persistently warns that linked files remain live; an unexpected clone error
  never silently selects that fallback.
- Captured path autolinks and glossary definitions, if implemented, replay only
  already-known presentation results. Shares expose no arbitrary path/glossary
  query and introduce no new abstraction into the standard renderer; omitting
  all such enrichment still passes acceptance.
- The manager can revoke one link, all links for a session through the existing
  contract, or every link globally, and accurately distinguishes valid links
  from connected viewers. Replacing or reopening a viewer token never defeats
  link revocation and is never presented as equivalent to it.
- Existing links remain inspectable and revocable when relay configuration is
  missing, Remote Access is disabled, or the relay is offline; those states
  disable creation/reachability without disabling local owner management.
- Disabling Public Read-Only Share immediately gates reads and creation,
  confirms and revokes all valid links, and cannot resurrect an interrupted
  disable's links after re-enable.
- Focused tests, capability audit, lint, and client console scan complete with
  zero warnings; final desktop and phone captures show the requested flow.

## Known design edges to settle during implementation

- Choose the bounded retry status/code and client presentation while legacy
  migration runs; do not make retryable unavailability look like revocation.
- Confirm that every public file-capability decision can be precomputed into
  bounded snapshot metadata before adopting parse-free streaming.
- Define the supported CoW clone primitive, excluded Git metadata, size/time
  reporting, and cleanup behavior without building a general worktree-snapshot
  abstraction for non-share code.
- Settle the legacy empty-message frozen-body repair inside migration rather
  than retaining the current serve-time full-session fallback indefinitely.
- Set pagination defaults and maximums from compact-record measurements, not
  transcript sizes.
- Decide whether the specialized legacy parser is small enough to keep
  in-tree; if not, justify a narrowly scoped streaming-parser dependency
  against the project's minimalist-runtime policy before adding it.
- Decide when the retained legacy backup may be removed. Migration success
  alone should not silently destroy the only rollback source.
